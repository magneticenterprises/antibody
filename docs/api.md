# API Reference

**`openapi/openapi.json` is the source of truth** for HTTP paths, parameters, and schemas. The `antibody-api openapi` command generates this file from the Rust endpoint types, and CI fails if the file drifts. MCP tool schemas are in `openapi/mcp-tools.json` (generated by `antibody-api mcp-schema`).

- **Base URL:** The value of `ANTIBODY_PUBLIC_URL`.
- **Content-Type:** All request and response bodies use `application/json`. Any other media type returns `415 unsupported_media_type`.
- **Request ID:** Every response includes an `X-Request-Id` header. If the client sends a valid `X-Request-Id` (alphanumeric characters and `-`, up to 64 characters), the server echoes it.

## Transport

The API accepts plain HTTP only from client IP addresses inside `ANTIBODY_HTTP_TRUSTED_NETWORKS` (default: loopback). All other requests require HTTPS (`X-Forwarded-Proto: https` from a trusted proxy when `ANTIBODY_TRUST_PROXY=true`). Unencrypted requests from untrusted networks return `403 forbidden`. Health endpoints are exempt. See [`security.md`](security.md).

## Authentication

| Method | Clients | Mechanism |
| --- | --- | --- |
| API token | Agent hooks, MCP, CI, scripts | Send `Authorization: Bearer abt_...`. Tokens belong to a principal, hold scopes, and support an optional repository allow-list and expiration date. The database stores only a SHA-256 hash. |
| Browser session | Web dashboard | Send `POST /v1/auth/login` with username and password. The server sets an `HttpOnly`, `SameSite=Strict` cookie (`antibody_session`, or `__Host-antibody_session` with `Secure` over HTTPS) and returns a `csrf_token`. Mutating cookie requests must send `X-CSRF-Token` and a matching `Origin` header. |
| Webhook signature | GitHub, generic CI | Send an HMAC-SHA256 signature header over the raw request body. See [Webhooks](#webhooks). |

### Roles and Scopes

Principals have one of two roles:

- `admin`: Accesses all repositories in the organization and all admin endpoints.
- `member`: Accesses only repositories granted with `read` or `write` permission.

Disconnected repositories are excluded from all scopes. A token cannot exceed the permissions of its principal.

| Scope | Permitted Operations |
| --- | --- |
| `sessions:write` | `POST /v1/sessions` (also requires a `write` grant on the repository), `GET /v1/sessions/{id}` |
| `context:read` | Search, solutions, hooks endpoint, MCP `find_relevant_context` and `get_solution`, overview, activity, session list |
| `outcomes:write` | `POST /v1/outcomes`, MCP `report_outcome` |
| `admin` | All `/v1/admin/*` endpoints, repository management, solution state changes, session deletion, and transcript access. Includes all other scopes implicitly. |
| `ci:write` | Reserved for future use (CI webhooks use HMAC signatures). |

The server checks repository authorization before search, ranking, and source expansion. Missing repositories and unauthorized repositories return the same `repository_access_denied` error.

## Errors

All HTTP errors return this JSON structure:

```json
{
  "error": {
    "code": "repository_access_denied",
    "message": "...",
    "request_id": "..."
  }
}
```

| Error Code | HTTP Status | Meaning |
| --- | --- | --- |
| `unauthenticated` | `401` | Missing, malformed, expired, or revoked credentials (`WWW-Authenticate: Bearer`). |
| `invalid_signature` | `401` | Webhook signature, timestamp, or organization check failed. |
| `forbidden` | `403` | Authenticated, but missing required scope/role or using plain HTTP from an untrusted network. |
| `repository_access_denied` | `403` | Repository does not exist or the caller lacks access. |
| `csrf_failed` | `403` | Browser request has a missing or invalid `X-CSRF-Token` or cross-origin `Origin` header. |
| `not_found` | `404` | Resource does not exist or is outside the caller's scope. |
| `invalid_request` | `400` | Schema, validation, or size limit violation. |
| `idempotency_key_required` | `400` | `Idempotency-Key` header is missing or invalid. |
| `payload_too_large` | `413` | Request body exceeds the endpoint byte limit. |
| `unsupported_media_type` | `415` | `Content-Type` is not `application/json`. |
| `idempotency_conflict` | `409` | `Idempotency-Key` was already used with a different request body. |
| `invalid_state_transition` | `409` | Requested state change is invalid from the current state. |
| `replayed_delivery` | `409` | Webhook delivery ID was already processed. |
| `conflict` | `409` | Uniqueness conflict (for example, a duplicate username). |
| `rate_limited` | `429` | Rate limit exceeded (`Retry-After: 10`). |
| `service_unavailable` | `503` | A required dependency is unavailable. |
| `internal` | `500` | Unexpected server error. Details are logged on the server only. |

MCP tool errors return a tool result with `isError: true` and text `<code>: <message>`.

## Session Ingestion Rules

- **Idempotency key:** Require an `Idempotency-Key` header with 8 to 200 characters matching `[A-Za-z0-9._:-]`. Keys are unique per organization.
- **Retries:** Retrying with the exact same key and byte-identical body returns `202` with the original `id` and `duplicate: true`. Reusing a key with a different body returns `409 idempotency_conflict`.
- **Validation:** The server rejects requests that have neither `messages` nor `hints`, more than 2,000 messages, a message over 100,000 characters, NUL bytes, an invalid `owner/name` repository, or a non-hexadecimal `revision`.
- **Capture mode:** Organization settings control capture mode. By default (`structured_only`), the worker deletes the redacted payload as soon as extraction finishes. When an administrator enables `raw_capture_enabled`, the database keeps the redacted payload for `raw_retention_days`.
- **Untrusted hints:** Client `hints.*` fields and test claims record untrusted `agent_claim` evidence and never verify a solution.

## Limits

| Limit | Default | Environment Variable |
| --- | --- | --- |
| `POST /v1/sessions` body | `2 MiB` | `ANTIBODY_MAX_SESSION_BYTES` |
| Webhook bodies | `5 MiB` | `ANTIBODY_MAX_WEBHOOK_BYTES` |
| Other JSON bodies and `/mcp` | `256 KiB` | `ANTIBODY_MAX_JSON_BYTES` |
| Search `task` / `error` length | `8,000` / `20,000` chars | Fixed |
| Search `files` / `dependencies` count | `200` / `500` items | Fixed |
| Suggestions per search | `3` (`limit` 1 to 3) | Fixed |
| General rate limit | `600` requests/min | `ANTIBODY_RATE_LIMIT_PER_MINUTE` |
| Login rate limit | `10` attempts/min | `ANTIBODY_LOGIN_RATE_LIMIT_PER_MINUTE` |
| Search time budget | `1200` ms indexed, `400` ms embedding | `ANTIBODY_SEARCH_TIMEOUT_MS`, `ANTIBODY_EMBED_TIMEOUT_MS` |

## Search and Outcomes

`POST /v1/context/search` requires `task` or `error` and accepts optional `repository`, `revision`, `component_path`, `files`, `dependencies`, `platform`, `limit`, `include_incompatible`, and `agent_session_id`.

The response returns:

- `retrieval_id`
- Up to three `suggestions`
- `degraded` and `degraded_reasons`
- `suppressed_incompatible`
- `latency_ms`
- An untrusted-content `notice`

To report how an agent used a suggestion, send `retrieval_id` and `solution_id` to `POST /v1/outcomes` with `outcome` set to `used`, `rejected`, or `inapplicable`.

## Webhooks

Antibody derives per-organization webhook secrets from `ANTIBODY_SECRET_KEY` and the organization's `webhook_secret_version`. Administrators view or rotate secrets with `POST /v1/admin/webhook-secrets` (`{"rotate": true}` invalidates old secrets immediately).

### GitHub (`POST /v1/webhooks/github?org=<slug>`)

- **Headers:** `X-Hub-Signature-256: sha256=<hex>`, `X-GitHub-Event`, `X-GitHub-Delivery`.
- **Supported events:** `ping`, `push`, `pull_request`, `check_run`, `workflow_run`, `deployment_status`, `repository`, and membership/team audit events.

### Generic CI (`POST /v1/webhooks/ci`)

| Header | Value |
| --- | --- |
| `X-Antibody-Org` | Organization slug (optional when hosting a single organization) |
| `X-Antibody-Delivery` | Unique delivery ID (`1` to `128` characters from `[A-Za-z0-9._-]`) |
| `X-Antibody-Timestamp` | Unix timestamp in seconds (must be within 300 seconds of server time) |
| `X-Antibody-Signature` | `sha256=` followed by hex HMAC-SHA256 of `"<timestamp>.<raw body>"` |

Example request:

```sh
ts=$(date +%s)
sig=$(printf '%s.%s' "$ts" "$body" | openssl dgst -sha256 -hmac "$ANTIBODY_CI_SECRET" -hex | sed 's/^.* //')
curl -X POST "$ANTIBODY_URL/v1/webhooks/ci" \
  -H 'Content-Type: application/json' \
  -H "X-Antibody-Org: $ORG" \
  -H "X-Antibody-Delivery: $(uuidgen)" \
  -H "X-Antibody-Timestamp: $ts" \
  -H "X-Antibody-Signature: sha256=$sig" \
  --data-binary "$body"
```

## MCP Server

`/mcp` serves the Model Context Protocol over streamable HTTP using bearer tokens. It exposes three read/report tools and never exposes shell, file-write, or code-execution tools:

| Tool | Required Scope | Purpose |
| --- | --- | --- |
| `find_relevant_context` | `context:read` | Searches for matching solutions (same as `POST /v1/context/search`). |
| `get_solution` | `context:read` | Fetches full solution details and evidence (same as `GET /v1/solutions/{id}`). |
| `report_outcome` | `outcomes:write` | Reports whether a solution was `used`, `rejected`, or `inapplicable` (same as `POST /v1/outcomes`). |
