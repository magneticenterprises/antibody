# Antibody web dashboard

A static React single-page app for Antibody: overview, repositories, knowledge, activity
and administration. It talks only to the same-origin Rust HTTP API under `/v1/…`, never
to model providers or the database. The production build is plain files in `dist/`,
served by Caddy next to the API (see `deploy/Dockerfile.web`).

Stack: React 19, strict TypeScript, Vite, react-router, `openapi-fetch` with types
generated by `openapi-typescript`, plain CSS with custom properties (light and dark
themes follow `prefers-color-scheme`). There is no UI kit, no CSS-in-JS and no external
font or CDN request.

## Requirements

- Node 26 (`.nvmrc`)
- pnpm 12.14.0 (`packageManager` in `package.json`; `corepack enable` picks it up)

```sh
pnpm install
```

## Scripts

| Script | What it does |
| --- | --- |
| `pnpm dev` | Vite dev server on http://localhost:5173. `/v1` and `/mcp` are proxied to `http://127.0.0.1:18080`; set `ANTIBODY_API_PROXY` to use a different address. |
| `pnpm build` | `tsc --noEmit`, then a production build into `dist/` with a strict CSP meta tag. |
| `pnpm preview` | Serves `dist/` on http://localhost:4173 with the same proxy. |
| `pnpm run gen:api` | Regenerates `src/api/schema.d.ts` from `../../openapi/openapi.json`. |
| `pnpm run check:api` | Regenerates into a temporary file and fails if the result differs from the committed `schema.d.ts` (contract drift check). |
| `pnpm test` | Vitest and React Testing Library in jsdom, with `fetch` mocked. |
| `pnpm exec playwright test` | End-to-end tests against the real backend (see below). |

## Running against a local API

The API rejects mutating cookie requests whose `Origin` is not `ANTIBODY_PUBLIC_URL`,
so set it to the origin you open in the browser:

```sh
# from the repository root, with Postgres from deploy/compose.dev.yaml
export DATABASE_URL=postgres://antibody:antibody@127.0.0.1:55432/antibody
export ANTIBODY_SECRET_KEY=change-me-change-me-change-me-0123456789
export ANTIBODY_BIND=127.0.0.1:18080
export ANTIBODY_PUBLIC_URL=http://localhost:5173   # 4173 when using `pnpm preview`
./target/debug/antibody-api serve

# in apps/web
pnpm dev
```

## API contract

- `openapi/openapi.json` is generated from the Rust code and is authoritative.
  `pnpm run gen:api` turns it into `src/api/schema.d.ts`. `src/api/types.ts` only
  aliases `components["schemas"][…]`; request and response models are never written
  by hand.
- `scripts/api-codegen.mjs` uses openapi-typescript's default lint rules, so a duplicate
  `operationId` (which would merge two endpoints' types) fails generation and
  `check:api`.
- Runtime enum lists (for selects and checkboxes) are checked against the schema
  types. If the schema gains a value, `tsc` fails until the list is updated.
- "Try a search" calls `POST /v1/context/search?preview=true`. The server runs the
  same authorized search but records no retrieval, so previews never count as usage
  and cannot receive outcomes.

## Authentication and security

- `POST /v1/auth/login` sets an HttpOnly, SameSite=Strict session cookie. On load,
  `GET /v1/auth/session` restores the session.
- The CSRF token from `SessionInfo` is kept only in module memory (`src/api/client.ts`).
  It is never written to Web Storage, and after a reload it is fetched again from
  `GET /v1/auth/session`. An openapi-fetch middleware adds `X-CSRF-Token` to every
  POST, PUT, PATCH and DELETE.
- A 401 from any call returns the user to the sign-in page. Admin-only views and
  actions are hidden for members, but the API stays authoritative: 403 responses show
  an "Access denied" state that includes the request id.
- Every API-derived string is rendered as text: no `dangerouslySetInnerHTML` and no
  Markdown. External links open only for `http(s)` URLs, with
  `rel="noopener noreferrer"`. Raw transcripts and webhook secrets appear only after an
  explicit confirmation that says the access is audited.

## Layout

```
src/api/         generated schema, typed client (+ CSRF middleware), error normalization
src/auth/        session context (login, logout, session probing)
src/components/  layout, badges, status states (loading/empty/error/forbidden/stale), confirmations
src/hooks/       useQuery (small fetch hook), useAction, useNow
src/routes/      one folder or file per route: overview, repositories, knowledge, activity, settings
e2e/             Playwright tests and the real-backend harness
scripts/         API code generation and the drift check
```

Every route shows explicit loading, empty, error, forbidden and stale states. Data
older than 60 seconds is marked "Stale" and has a refresh button.

## End-to-end tests (real backend)

Prerequisites:

1. Postgres with pgvector on `127.0.0.1:55432` (user and password `antibody`), for
   example from `deploy/compose.dev.yaml`.
2. The Rust binaries: `cargo build -p antibody-api -p antibody-worker` (from the
   repository root).
3. The Chromium build used by Playwright: `pnpm exec playwright install chromium`.

Run:

```sh
pnpm exec playwright test
```

What happens:

- **`globalSetup`** (`e2e/global-setup.ts` and `e2e/backend.ts`):
  1. Drops and recreates the `antibody_e2e` database with `psql`. Never point it at a
     database you care about.
  2. Runs `antibody-api bootstrap` (organization `demo`, user `admin`) and reads the
     admin API token from its JSON output.
  3. Starts `antibody-api serve` on `127.0.0.1:18080` with
     `ANTIBODY_PUBLIC_URL=http://localhost:4173` and relaxed login and request rate
     limits. It fails fast if something already listens on that port.
  4. Seeds data through the HTTP API with the admin token: creates the repository
     `acme/api`, turns on raw capture, ingests one session (a tool error
     `error[E0308]: mismatched types` and a final fix message), runs
     `antibody-worker --once` so extraction finishes, then creates a `member` user
     with a read grant.
  5. Passes the seed IDs to the tests in `E2E_SEED`. The teardown it returns stops the
     API.
- **`webServer`** builds the app and runs `vite preview` on http://localhost:4173,
  proxying `/v1` to the API. Playwright stops it when the run ends.

The tests cover:

- a bad login, showing the error message and request id;
- the admin path: overview, knowledge search, solution detail with untrusted agent
  claims, verifying through the UI (which exercises cookie and CSRF), the activity
  session and the audited transcript view;
- the admin path in Settings: a token created with colon scopes such as
  `context:read`, shown exactly once and then used as a bearer token, the grant list,
  a workflow proposal and the audit log;
- a search preview that adds no retrieval, compared with a non-preview search that
  does;
- a member: no Settings link, a forbidden view for admin pages, a real 403 from an
  admin endpoint, no admin actions, and sign-out.

Environment overrides: `E2E_PGHOST`, `E2E_PGPORT`, `E2E_PGUSER`, `E2E_PGPASSWORD`,
`E2E_PGDATABASE`, `E2E_API_PORT` (also used for the preview proxy), `E2E_ADMIN_PASSWORD`,
`E2E_MEMBER_PASSWORD`.
